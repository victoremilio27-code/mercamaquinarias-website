## D-01 · Un control se delimita; un filete decora. No es lo mismo y no lleva el mismo token

`--app-borde-control` **sustituye** a `--app-line` en todo lo que es un control.
`--app-line` **se queda como está** para los filetes entre contenido: a 1.30:1
están bien porque no delimitan nada pulsable, y subirlos a 3:1 llenaría el sitio
de rayas duras que nadie pidió.

Los dieciséis controles, tal como los listó el plan aprobado:

`.btn--linea`, `.btn-tabla`, `select`, `input`, `textarea`, `.campo-v`,
`.campo-doble`, `.chip`, `.paginacion__it`, `.tema-toggle`, `.cab__cuenta`,
`.cab__toggle`, `.heroe__atajos a`, `.carrusel__flecha`, `.perfil__red`,
`.filtros__abrir`.

## D-02 · El ámbar tiene dos papeles y hoy comparte un solo token

`--ambar-hondo` aparece **78 veces** en la hoja. Medido al planificar, por
propiedad:

| propiedad | veces | qué hacer |
|---|---|---|
| `color` | 64 | Clasificar uno a uno. Sobre superficie clara → `--ambar-texto`. Sobre superficie oscura fija (mosaico, sello, banda del vídeo) → **se queda**. |
| `accent-color` | 5 | **Se queda.** Es el relleno de casillas y radios marcados, no texto: el ámbar de marca es lo correcto. |
| `background` | 3 | **Se queda.** `.btn--ambar:hover`, `.plan__cinta` y compañía: el valor actual es el correcto. |
| `border-color`, `border-left-color` | 2 | **Se quedan.** Son realce de marca, no borde de control: el borde de control ya lo pone D-01. |
| `text-decoration-color` | 1 | Va con el `color` de su regla: si el texto pasa a `--ambar-texto`, el subrayado también. |
| declaración del token + comentario | 2 | No son usos. |

Los que el plan aprobado nombró como texto, para empezar por ellos:
`.form__enlaces a`, `.celda-equipo__nombre:hover`, `.invitacion-dealer a`,
`.estado--pausado`, `.pie__lista a:hover`.

**No hay atajo.** Un `sed` sobre `color: var(--ambar-hondo)` convertiría también
los que van sobre superficie oscura fija y los dejaría ilegibles en un sitio
donde hoy se leen bien. Se miran los 64 uno a uno.

## D-03 · Quien dice si esto quedó bien es el comprobador, no el ojo

El plan 02-03 dejó `npm run check:contraste` funcionando y agrupando los
hallazgos en cuatro tipos con nombre: `texto`, `control`, `dinamismo` y
`navegacion`. Este plan cierra cuando el tipo `control` desaparece de su salida.
Las comprobaciones automáticas de abajo son exactamente eso, no un `grep` sobre
la hoja: un `grep` diría que el token está escrito, no que el contraste se
alcanza.

Al cerrar este plan **seguirá habiendo hallazgos** de tipo `texto` y
`dinamismo` —son los literales que convierte el plan 02-05— y eso está bien. Lo
que no puede quedar es un solo `control`.

## D-04 · Cómo se corre el comprobador durante este plan

Necesita el sitio levantado y la base sembrada, igual que las auditorías:

```
npm run db:demo
npm start &
node tools/esperar-servidor.js --url http://127.0.0.1:8080/
node tools/check-contraste.js
```

Si el comprobador imprime hallazgos de tipo `navegacion`, el sitio no está
arriba o la base no está sembrada: eso no es un fallo de este plan.
