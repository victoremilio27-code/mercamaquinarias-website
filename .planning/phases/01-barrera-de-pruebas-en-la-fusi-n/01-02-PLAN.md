<objective>
Convertir el flujo del plan `01-01` en una barrera de verdad: que GitHub
impida la fusión cuando una comprobación está en rojo, y demostrarlo con un
Pull Request deliberadamente roto.

Purpose: el flujo por sí solo informa; lo que bloquea es la protección de
rama. Y una barrera que nadie ha visto detener nada no se sabe si detiene algo.
Output: `main` protegida con comprobaciones obligatorias, y la prueba
documentada de que un PR en rojo no se puede fusionar.
</objective>

Victor: esto es lo único de esta fase que no puede hacer Claude. Son dos
minutos.

**Paso 1 — Fusionar primero el PR del plan `01-01`.** Su número está en
`01-01-SUMMARY.md`. Todavía no hay protección, así que se fusiona con el botón
normal. Al fusionarse, el flujo correrá sobre `main` y desplegará: es la
primera vez que un despliegue va detrás de las pruebas.

**Paso 2 — Proteger `main`:**

1. Abrir el repositorio en GitHub → pestaña **Settings**.
2. Menú izquierdo → **Branches** → botón **Add branch protection rule**
   (si el repositorio ya usa el sistema nuevo, aparece como
   **Rules → Rulesets → New branch ruleset**; las casillas se llaman igual).
3. En **Branch name pattern**, escribir exactamente: `main`
4. Marcar **Require a pull request before merging**.
   - Dejar **Require approvals** en 0 si no se quiere revisión mutua
     obligatoria. Esta fase no lo exige; es decisión aparte.
5. Marcar **Require status checks to pass before merging**.
   - Marcar también **Require branches to be up to date before merging**.
     Esto importa con dos personas: obliga a que la rama incorpore lo último
     de `main` antes de fusionar, y es lo que hace que las pruebas midan el
     código que va a quedar y no uno que ya no existe.
   - En el buscador de comprobaciones, escribir `pruebas` y seleccionarla.
     Repetir con `navegador`. **Tienen que quedar las dos en la lista.**
     Si el buscador no las encuentra, es que el PR del paso 1 no llegó a
     correr: revisar la pestaña Actions antes de seguir.
6. Marcar **Block force pushes** (o dejar desmarcado *Allow force pushes*) y
   **Restrict deletions**. Nunca se reescribe historial en este repositorio.
7. Marcar **Do not allow bypassing the above settings**. Sin esto, la barrera
   no protege a quien tenga permiso de administrador, y la idea es que proteja
   a las dos personas por igual. Si algún día hace falta desplegar un arreglo
   urgente, la salida es desmarcar esta casilla un momento —queda registrado—
   o relanzar el despliegue a mano desde la pestaña **Actions**, no dejar un
   agujero permanente.
8. **Create** / **Save changes**.

**Paso 3 — Confirmar que quedó puesto:** volver a Settings → Branches y
comprobar que la regla de `main` lista `pruebas` y `navegador` como
comprobaciones obligatorias.

<task type="auto">
  <name>Tarea 2: demostrar que un Pull Request en rojo no se puede fusionar</name>
  <files>(ninguno de forma permanente: rama desechable que se borra al terminar)</files>
  <action>
Provocar un rojo a propósito y comprobar que GitHub bloquea la fusión. Es la
única manera de saber que la barrera existe de verdad y no solo en los ajustes.

1. Partiendo de `main` actualizada, crear la rama desechable
   `prueba/barrera-en-rojo`.
2. Romper **una sola** aserción en `tools/numero-a-letras.prueba.js`: cambiar
   el valor esperado de uno de los casos por otro que sea evidentemente falso,
   y dejar un comentario en la misma línea diciendo que es una rotura
   deliberada para comprobar la barrera. Se elige este archivo por tres
   razones: corre en el job `pruebas`, que es el rápido; es `node:test`, así
   que el fallo se lee limpio; y no es código de la aplicación, así que ni
   rozarlo puede afectar a producción.
3. Confirmar, empujar la rama y abrir el PR con `gh pr create`, con título y
   descripción en español que digan en la primera línea que es un PR de prueba
   que **no se fusiona**, para que la otra persona no se lleve un susto si lo
   ve pasar.
4. Esperar a que termine la pasada y comprobar tres cosas, guardando la salida
   literal para el SUMMARY:
   - `gh pr checks` muestra `pruebas` en **fail** y el paso que cayó es el de
     `facturas:letras`.
   - `gh run view --log-failed` de esa pasada muestra la salida del fallo: el
     nombre del caso de prueba, el valor esperado y el recibido. Esto es lo que
     hace que cualquiera de las dos personas sepa qué se rompió sin entrar al
     VPS; copiar tres o cuatro líneas de esa salida al SUMMARY como evidencia.
   - `gh pr view --json mergeStateStatus,mergeable` devuelve un estado que
     bloquea la fusión (`BLOCKED`). Si devolviera `CLEAN`, la protección del
     paso anterior no quedó bien puesta: **parar y decirlo**, no fusionar nada.
5. Comprobar además que en esa misma pasada el job `desplegar` no corrió.
6. Deshacer sin rastro: cerrar el PR con `gh pr close --delete-branch`, volver
   a `main` y borrar la rama local. **El PR no se fusiona nunca** y
   `tools/numero-a-letras.prueba.js` queda en `main` exactamente como estaba.
7. Verificar que quedó limpio: `git status` sin cambios y
   `git diff main -- tools/numero-a-letras.prueba.js` vacío.

No usar `--force` en ningún momento ni empujar a `main`.
  </action>
  <verify>
    <automated>git rev-parse --abbrev-ref HEAD | grep -qx main &amp;&amp; test -z "$(git status --porcelain)" &amp;&amp; git diff --quiet origin/main -- tools/numero-a-letras.prueba.js &amp;&amp; npm run facturas:letras &amp;&amp; ! git ls-remote --exit-code --heads origin prueba/barrera-en-rojo &amp;&amp; echo "rojo demostrado y repositorio limpio"</automated>
  </verify>
  <done>Queda registrada en el SUMMARY la salida literal del fallo y el `mergeStateStatus` bloqueado del PR de prueba. La rama desechable ya no existe ni en local ni en remoto, `npm run facturas:letras` vuelve a pasar en `main`, y el job `desplegar` no corrió en la pasada roja.</done>
</task>
