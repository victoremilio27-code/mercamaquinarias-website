## Tarea 1 — Migración y funciones de base (`tools/db.js`)

Añade AL FINAL de `MIGRACIONES` (nunca reescribas una anterior) `['2026-10-cuenta-recuperacion', [...]]`:

```sql
CREATE TABLE IF NOT EXISTS cambios_correo (
  id TEXT PRIMARY KEY,
  usuario_id TEXT NOT NULL REFERENCES usuarios(id),
  anterior TEXT NOT NULL,
  nuevo TEXT NOT NULL,
  via TEXT NOT NULL CHECK (via IN ('usuario','recuperacion','reversion')),
  creado TEXT NOT NULL,
  ip TEXT,
  revertir_hash TEXT,
  revertir_expira TEXT,
  revertido TEXT,
  solicitud_id TEXT
);
CREATE INDEX IF NOT EXISTS ix_cambios_correo_usuario ON cambios_correo (usuario_id);
CREATE UNIQUE INDEX IF NOT EXISTS ux_cambios_correo_revertir ON cambios_correo (revertir_hash);
CREATE TABLE IF NOT EXISTS solicitudes_recuperacion (
  id TEXT PRIMARY KEY,
  referencia TEXT NOT NULL UNIQUE,
  correo_cuenta TEXT NOT NULL,
  usuario_id TEXT REFERENCES usuarios(id),
  correo_contacto TEXT NOT NULL,
  nombre TEXT NOT NULL,
  telefono TEXT,
  rnc TEXT,
  detalle TEXT NOT NULL,
  estado TEXT NOT NULL DEFAULT 'pendiente'
    CHECK (estado IN ('pendiente','aprobada','rechazada','anulada')),
  creada TEXT NOT NULL,
  resolver_desde TEXT NOT NULL,
  resuelta TEXT,
  resuelta_por TEXT REFERENCES usuarios(id),
  motivo TEXT,
  ip TEXT
);
CREATE INDEX IF NOT EXISTS ix_recuperacion_estado ON solicitudes_recuperacion (estado, creada);
CREATE INDEX IF NOT EXISTS ix_recuperacion_usuario ON solicitudes_recuperacion (usuario_id);
```

(`UNIQUE` con varios NULL es válido en SQLite.) Comprueba cómo declaran índices y FK las migraciones
vecinas y sigue su estilo.

Añade `cambio_correo: 15` a `MINUTOS_CODIGO`. Añade a `ACCIONES_BITACORA`
`'cuenta.recuperar': 'Cuenta recuperada: correo cambiado tras comprobar identidad'`.

Funciones nuevas (exportadas), síncronas, cada escritura múltiple en su transacción (mira cómo lo hacen
las vecinas: `BEGIN`/`COMMIT` o `SAVEPOINT` cuando pueda ir dentro de `enNombreDe`):

- `cerrarOtrasDe(idUsuario, testigoActual)`: borra las sesiones del usuario salvo la actual y todos sus
  `dispositivos`.
- `cambiarCorreo({ idUsuario, nuevo, via, ip, verificado, conReversion, solicitudId })` →
  `{ anterior, nuevo, testigoRevertir }`. Normaliza a minúsculas; lanza con `codigo = 409` si otro usuario
  tiene ese correo; actualiza `usuarios.correo` y `correo_verificado`; actualiza `organizaciones.correo`
  **solo** de la organización del usuario cuyo `correo` sea el anterior; marca consumidos los `codigos`
  pendientes del correo anterior; inserta en `cambios_correo`. Si `conReversion`, genera un testigo de
  32 bytes hex, guarda su HMAC (reutiliza el HMAC con `SECRETO` de `firmarCodigo` o uno equivalente) y
  `revertir_expira = +7 días`. Usa SAVEPOINT (se llamará dentro de `enNombreDe`).
- `revertirCambioCorreo(testigo, ip)` → `{ ok:true, idUsuario, correo }` o `{ ok:false, motivo }` con
  motivos `inexistente | vencido | usado | ocupado`. Busca por HMAC, comprueba vigencia y no revertido;
  si el `anterior` lo tiene otro usuario → `ocupado`. Aplica: correo = anterior, verificado 1, organización
  de vuelta si su correo era el `nuevo`, `revertido = ahora`, fila `via='reversion'` sin testigo, y pone
  `revertir_hash = NULL` en las filas del mismo usuario con `creado >= ` la usada y sin revertir. Una sola
  transacción; la marca de usado va en una sentencia condicional (`... AND revertido IS NULL`) como hace
  `verificarCodigo`.
- `anularClave(idUsuario)`: pone una contraseña aleatoria de 32 bytes (reutiliza `cambiarClave`).
- Solicitudes: `crearSolicitudRecuperacion({ correoCuenta, correoContacto, nombre, telefono, rnc,
  detalle, ip })` → la fila creada o `null` si ya hay una `pendiente` para ese `correo_cuenta`. Busca el
  usuario por correo (puede ser NULL). Referencia `REC-` + 6 caracteres de un alfabeto sin ambigüedades
  (mira cómo se generan otras referencias en el archivo y reutiliza). `resolver_desde = creada + 72 h`
  (constante `HORAS_ESPERA_RECUPERACION = 72` exportada).
- `solicitudRecuperacion(id)`, `solicitudesRecuperacion({ estado })` (más reciente primero, tope 200).
- `expedienteRecuperacion(id)`: la solicitud más, si hay usuario, `cuenta: { nombre, correo, telefono,
  creado, correo_verificado }`, `organizacion: { tipo, nombre, rnc, estado_revision }`, `anuncios` (cuántos
  y los títulos de hasta 5), `pagos` (los 5 últimos: fecha, referencia, total, estado, NCF si lo hay),
  `telefonosVerificados`, `cambiosCorreo` (los 5 últimos). Mira nombres reales de columnas antes de
  escribir el SQL.
- `anularRecuperacionesDe(idUsuario, motivo)` → número de filas pasadas de `pendiente` a `anulada`.
- `resolverRecuperacion({ id, estado, idAdmin, motivo })`: `pendiente` → `aprobada|rechazada` con
  sentencia condicional; lanza 409 si ya no está pendiente.

## Tarea 2 — Correos (`tools/correo.js`)

Sigue el estilo de `enviarAvisoCambioClave` (texto + `envoltura`, `responderA: BUZONES.soporte`, trato de
usted). Exporta:

- `plantillaCodigo`: tipo `cambio_correo` → asunto `${codigo} es su código para cambiar de correo ·
  MercaMaquinarias`, cuerpo «Use este código para confirmar que esta dirección será el nuevo correo de su
  cuenta.»
- `enviarAvisoCambioCorreo({ para, nombre, nuevo, enlaceRevertir })` al correo ANTERIOR: el correo nuevo
  **enmascarado** (`j***@dominio.com`, función `enmascararCorreo` exportada), y si no fue usted, el
  enlace (vale 7 días) que devuelve la cuenta a este correo y anula la contraseña. Sin enlace cuando
  `enlaceRevertir` es null (recuperación aprobada): entonces remite a soporte.
- `enviarCorreoCambiado({ para, nombre })` al NUEVO: confirmación.
- `enviarRecuperacionRecibida({ para, nombre, referencia, desde })` al contacto: acuse, no se resuelve
  antes de `desde`, podemos pedirle datos por este correo, nunca por teléfono.
- `enviarAvisoRecuperacionAlTitular({ para, nombre, contactoEnmascarado, desde })` al correo de la
  cuenta: alguien pidió pasar su cuenta a otro correo; si fue usted no haga nada; si no, **entre a su
  cuenta y la solicitud se anula sola**, y cambie la contraseña.
- `avisarRecuperacionInterna(solicitud)` → `avisarInternamente({ buzon: 'soporte', ... })` con los datos y
  «Revísela en /admin.html a partir de …».
- `enviarRecuperacionAprobada({ para, nombre })` al correo nuevo: la cuenta ya está en este correo; entre
  a `${SITIO}/cuenta.html`, «Olvidé mi contraseña», con este correo, para crear una contraseña.
- `enviarRecuperacionRechazada({ para, referencia })`: genérico, no pudimos comprobar que la cuenta sea
  suya; responda a este correo con más datos.

Los enlaces con `SITIO`. Fechas en hora dominicana (mira cómo formatean fechas otros correos del archivo).

## Tarea 3 — Rutas (`tools/api.js`)

Contrato exacto (lo consumen los planes 02 y 03; no cambies nombres ni formas):

| Método y ruta | Sesión | Cuerpo | Respuesta |
|---|---|---|---|
| `POST /api/cuenta/correo` | sí | `{ clave, correo }` | 202 `{ correo, minutos, mensaje }` |
| `POST /api/cuenta/correo/confirmar` | sí | `{ correo, codigo }` | 200 `sesionPublica` |
| `POST /api/cuenta/correo/revertir` | no | `{ testigo }` | 200 `{ verificacion:'restablecer', correo, mensaje }` |
| `POST /api/cuenta/clave` | sí | `{ actual, nueva }` | 200 `{ ok:true, mensaje }` |
| `POST /api/cuenta/cerrar-otras` | sí | — | 200 `{ ok:true, cerradas }` |
| `POST /api/cuenta/recuperacion` | no | `{ correoCuenta, correoContacto, nombre, telefono, rnc, detalle }` | 202 `{ mensaje }` (idéntica siempre) |
| `GET /api/admin/recuperaciones?estado=` | admin | — | 200 `{ solicitudes:[…] }` (por defecto `pendiente`; `todas` para todas) |
| `GET /api/admin/recuperaciones/:id` | admin | — | 200 `expedienteRecuperacion` |
| `POST /api/admin/recuperaciones/:id/aprobar` | admin + bitácora | `{ motivo }` | 200 `{ ok:true, solicitud }` |
| `POST /api/admin/recuperaciones/:id/rechazar` | admin | `{ motivo }` | 200 `{ ok:true, solicitud }` |

Reglas:

- `/api/cuenta/correo`: tope `cambio-correo:${idUsuario}` 5/60; contraseña con `db.claveCorrecta`
  (401 «La contraseña no es correcta»); `correoValido`; igual al actual → 400; ocupado → 409 «Ese correo
  ya tiene una cuenta»; `emitirCodigo({ correo: nuevo, tipo:'cambio_correo', idUsuario, nombre })`; si
  `limitado` → 429.
- `/confirmar`: tope `confirmar-correo:${idUsuario}` 20/15; `verificarCodigo({ correo, tipo:'cambio_correo' })`
  con los mismos mensajes que `verificar`; `r.usuario_id !== ctx.usuario.id` → 400 «Código incorrecto»;
  `db.cambiarCorreo({ via:'usuario', verificado:true, conReversion:true })` (409 si ocupado);
  `db.cerrarOtrasDe`; correos a anterior (con `${SITIO}/cuenta.html?revertir=<testigo>`; exporta o
  importa `SITIO` de correo.js sin duplicar la constante) y a nuevo; `anularRecuperacionesDe`.
- `/revertir`: tope por IP 10/15; testigo solo `[0-9a-f]{64}` (si no, 400 genérico); motivos →
  400 «El enlace no es válido o ya se usó», «El enlace venció…», 409 «Ese correo ya lo usa otra cuenta.
  Escríbanos a soporte». Tras revertir: `cerrarTodoDe`, `anularClave`, `anularRecuperacionesDe`,
  `emitirCodigo({ tipo:'restablecer' })` al correo recuperado.
- `/clave`: tope 5/60 por usuario; actual correcta; `claveDebil(nueva, correo)`; `cambiarClave`,
  `cerrarOtrasDe`, `enviarAvisoCambioClave`.
- `/recuperacion`: tope por IP `recuperacion:${ip}` 3/60 (429 si se pasa: eso no revela nada). Valida:
  los dos correos válidos y distintos; nombre; `detalle` de 20 a 2000 caracteres; `rnc` opcional con
  `rncValido`; teléfono opcional con `telefonoValido`. Crea la solicitud; si se creó, manda acuse al
  contacto, aviso al titular (si hay usuario) y aviso interno. Responde SIEMPRE 202 con el mismo mensaje.
- Anular al entrar: en `verificar` (éxito), en `entrar` (equipo de confianza), en `restablecer` (éxito)
  llama `db.anularRecuperacionesDe(u.id, 'El titular entró a su cuenta')`.
- Admin: `aprobar` con `conAdminEnNombreDe('cuenta.recuperar', …)`: 404 si no existe; 409 si no está
  pendiente, si no hay `usuario_id` («Sin cuenta detrás solo se puede rechazar»), o si `ahora <
  resolver_desde` («Podrá resolverse a partir de …»); motivo ≥ 15 caracteres (400). Dentro de
  `ctx.enNombreDe(idOrgDelUsuario, { objetoTipo:'solicitud_recuperacion', objetoId:id, motivo }, () => …)`:
  `cambiarCorreo({ via:'recuperacion', verificado:false, conReversion:false, solicitudId })` +
  `resolverRecuperacion` → `{ antes:{ correo: anterior }, despues:{ correo: nuevo, solicitud:'aprobada' } }`.
  Después: `cerrarTodoDe`, `enviarRecuperacionAprobada` al nuevo, `enviarAvisoCambioCorreo` (sin enlace)
  al anterior.
- `rechazar`: `conAdmin`, motivo ≥ 15, `resolverRecuperacion`, correo al contacto; añádela a
  `ESCRITURAS_ADMIN_PROPIAS` con su comentario (la manda un visitante; guarda `resuelta_por`).
- Rutas en `RUTAS` junto a las de cuenta; las específicas (`/correo/confirmar`, `/correo/revertir`,
  `/:id/aprobar`) ANTES de las genéricas si alguna regex pudiera solaparse.
- `ctx.testigo` es el testigo de la sesión actual (lo usa `salir`).

## Tarea 4 — Arnés `tools/probar-cuenta.js` + `npm run cuenta:probar` + paso de CI

Estilo de `tools/probar-bitacora.js`: base temporal en `.tmp/prueba-cuenta/`, variables de entorno
ANTES de `require('./db.js')`, `MERCA_CORREO=archivo`, contadores `bien`/`mal` y `process.exit(mal ? 1 :
0)`. Reutiliza cómo `probar-bitacora.js`/`probar-seguridad.js` fabrican `req`/`res` y sesiones, y cómo
leen el código enviado (mira dónde escribe `porArchivo` o si hay un gancho para capturar envíos).

Comprobaciones mínimas (≥ 35):

1. Cambio de correo: sin sesión 401; contraseña mala 401; correo ocupado 409; igual al actual 400; código
   al correo nuevo; código de otro usuario no vale; al confirmar cambian `usuarios.correo` y
   `organizaciones.correo` (particular), otra sesión del usuario queda cerrada y la actual sigue;
   dispositivos borrados; aviso al anterior con enlace `?revertir=`; fila en `cambios_correo`.
2. Dealer cuyo `organizaciones.correo` es otro buzón: no se toca.
3. Revertir: enlace válido devuelve el correo, cierra todo, la contraseña vieja ya no entra, llega código
   `restablecer`; segundo uso falla; testigo vencido falla (manipula `revertir_expira`); cadena A→B→C:
   revertir el primero inutiliza el testigo del segundo; `ocupado` si otro tomó el correo.
4. Cambiar contraseña con sesión: actual mala 401; débil 400; bien → las otras sesiones cerradas, la
   actual sigue, aviso enviado. `cerrar-otras` deja solo la actual.
5. Recuperación: respuesta idéntica (código y cuerpo) con correo existente e inexistente; segunda
   pendiente para el mismo correo no crea fila; tope por IP; aviso al titular y acuse al contacto;
   entrar a la cuenta la anula.
6. Admin: no admin → 404; aprobar antes de las 72 h → 409; con motivo corto → 400; tras mover
   `resolver_desde` al pasado → aprueba, cambia el correo con `correo_verificado = 0`, cierra sesiones,
   deja fila en `bitacora_admin` con `accion='cuenta.recuperar'`; aprobar otra vez → 409; sin cuenta
   detrás → 409; rechazar funciona y no toca la cuenta.
7. Tras aprobar, `recuperar` + `restablecer` con el correo nuevo deja entrar y marca verificado.

Añade `"cuenta:probar": "node tools/probar-cuenta.js"` a `package.json` (junto a sus vecinos) y un paso
`npm run cuenta:probar` en el trabajo `pruebas` de `.github/workflows/desplegar.yml` (LF obligatorio en ese
archivo: compruébalo con `file` después de editar), después de `bitacora:probar`.
